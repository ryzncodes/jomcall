# Channel and integration roadmap

Research date: 2026-10-15. Status: implementation recommendations, not connected production capabilities. This document extends the existing architecture's connector plan; it does not replace its build order. Research used provider documentation. No authenticated provider account, real number, paid transaction, or live customer data was tested.

## Product boundary

JomCall is a conversational CRM: one contact history joins normal phone calls, WhatsApp chats, WhatsApp calls, bookings, notes, consent, and staff ownership. Its first job remains answering inbound enquiries. A sales pipeline, campaigns, and a general-purpose workflow builder can follow when customer demand warrants them.

Normal phone calls and WhatsApp calls require separate transports. Sharing an agent and contact record does not make their transfer rules, permissions, delivery evidence, or billing interchangeable. Keep channel capabilities explicit on each connection.

Calendar integration is optional. Answering FAQs, taking a message, qualifying an enquiry, and handing off to staff do not require Google Calendar or any other scheduling SaaS. Without a working booking connector, collect a preferred time and label it a **booking request awaiting staff confirmation**. Never claim a slot is available or confirmed from static business hours alone. A future built-in calendar could replace an external provider only after it becomes the authoritative availability system, including staff capacity, conflicts, holidays, cancellation, and concurrency controls.

### WhatsApp calling decisions that affect the UI

- **Staff transfer:** the documented WhatsApp path cannot bridge to PSTN mobile/landline endpoints. Use a browser/VoIP staff session, or end the call and create a separate callback request with suitable permission. Do not reuse a normal-phone transfer button without a channel capability check. Both [Twilio](https://www.twilio.com/docs/voice/whatsapp-business-calling) and [360dialog](https://docs.360dialog.com/docs/messaging/calling) document this restriction.
- **Hosted versus self-hosted:** LiveKit's ready-made WhatsApp Connector currently requires LiveKit Cloud. Agents may run elsewhere, but self-hosted LiveKit servers are not supported by that connector. A fully self-hosted calling option needs its own evaluated SIP/WebRTC adapter. [LiveKit connector prerequisites](https://docs.livekit.io/telephony/connectors/whatsapp/).
- **Eligibility is separate from chat connection:** provider documentation lists a 2,000 business-initiated conversation eligibility threshold; 360dialog also excludes coexistence numbers from its calling path. Treat these as account/provider checks, not universal promises from a green “WhatsApp connected” badge. [360dialog eligibility](https://docs.360dialog.com/docs/messaging/calling).
- **Window evidence:** 360dialog documents that incoming WhatsApp calls, including unanswered calls, and answered outbound calls refresh the service window. Record the event that opened the window. This must not be generalized to a normal phone call. Its page also contains broad wording about templates opening a window; do not use a template send alone to infer permission for free-form messaging. Verify exact current Meta semantics before live enforcement. [Provider calling window documentation](https://docs.360dialog.com/docs/messaging/calling).
- **Delivery:** accepted, queued, sent, delivered, read and failed are different facts. Only confirmed status events advance delivery indicators; read receipts may be unavailable. Ambiguous send outcomes stay in review without blind resend. [Provider status lifecycle](https://www.twilio.com/docs/messaging/guides/outbound-message-status-in-status-callbacks).

Direct Meta calling and lead retrieval documentation returned HTTP 429 during this research. Calling conclusions above use official infrastructure-provider documentation as a fallback, not a direct Meta account entitlement check. Recheck current country availability, permission expiry/limits, eligibility and coexistence support in the selected provider account before implementation. Keep these policies configurable rather than frozen in UI code.

A successful tool response must contain a durable provider booking/event reference before the agent confirms a booking. Disconnected, expired-auth, conflicting, ambiguous and cancelled states must remain visible. Mock preview slots are sample data, never availability claims.

## Connector contract and release proof

Use the spec's manifest-backed connector boundary. Each connector declares authentication, supported actions, incoming events, account constraints and health. Tenant credentials belong server-side, encrypted and revocable. Display last successful sync, reconnect action and current failure instead of a permanent “connected” label.

Start with one-way import/export where possible. Add bidirectional sync only with external IDs, ownership rules, webhook deduplication, out-of-order event handling, retry limits and a reconciliation job. Export only the fields needed by that connector, and carry contact deletion/consent changes through an auditable policy.

Recommended order: normal inbound SIP and WhatsApp chat; one reliable calendar connector; optional Cal.com; evaluated WhatsApp calling; generic webhooks and Sheets; Microsoft 365; CRM and lead-source adapters; commerce/payment requests when a real customer workflow needs them. This preserves the architecture's inbound-first priority.

Before any connector is advertised as live, prove real account authorization, revocation, incoming events, one successful action, duplicate-event handling, timeout recovery and tenant isolation. For booking, additionally prove collision handling and cancellation sync. For voice, prove audio, disclosure, disconnect, fallback and channel-valid staff handoff. Current frontend mock interactions satisfy none of these production gates by themselves.
